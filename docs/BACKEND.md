# Сервер участника 2

## Запуск

1. `npm.cmd ci`.
2. Добавить `.env.local` по `.env.example`. Не публиковать файл с ключами.
3. Выполнить `supabase/schema.sql` в SQL Editor отдельного тестового проекта.
4. Установить `NEXT_PUBLIC_DATA_MODE=api`, `AI_MODE=live`, `OPENAI_MODEL` в доступную модель с Structured Outputs.
5. `npm.cmd run dev`. Открыть `/tasks/new`.

Все маршруты реализованы в `src/app/api/[...path]/route.ts`. Логика состояния — `src/lib/server/service.ts`, адаптер Supabase — `database.ts`. Существующие типы Task и функция рейтинга используются без переименований.

## Доступ и ограничения деморежима

Это общий демонстрационный бизнес-профиль: владельца задаёт сервер через `DEMO_OWNER_ID` (по умолчанию `demo-business`), а не браузер. Все вошедшие в демостенд пользователи могут разыгрывать обе роли, выбирать демокоманду и выполнять действия бизнеса. Это не регистрация и не индивидуальная авторизация.

В production API закрыт, пока не задан `DEMO_ACCESS_PASSWORD`. При заданном пароле HTTP Basic проверяется во всех режимах. Перед показом открыть `/api/health` в браузере и ввести имя `demo` и пароль, затем вернуться на главную страницу. Применять только HTTPS при удалённом размещении. Для локального npm run dev пароль необязателен; сервер по умолчанию следует запускать на loopback.

Перед полноценным публичным использованием нужны пользовательские сессии и права по ролям. Ограничитель AI допускает 10 запросов в минуту на процесс; он подходит для одного демонстрационного сервера, но не заменяет общий лимит для нескольких экземпляров.

## Реализованные операции

| Метод | URL | Результат |
|---|---|---|
| GET | `/api/health` | Проверка приложения, не проверка базы |
| POST | `/api/ai/questions` | `{questions, source}` |
| POST | `/api/ai/card` | `{content, source, evidence?}` |
| POST | `/api/tasks` | Task; id от клиента, повтор создания не перезаписывает данные |
| GET | `/api/tasks/:id` | Полный Task текущего бизнеса |
| PATCH | `/api/tasks/:id/draft` | Сохранённый Task |
| POST | `/api/tasks/:id/confirm` | Подтверждённый Task, `{acknowledged:true,expectedRevision}` |
| POST | `/api/tasks/:id/publish` | Опубликованный Task, `{expectedRevision}` |
| GET | `/api/tasks?industry=…&level=…` | PublishedTask[] |
| GET | `/api/catalog/:id` | PublishedTask без черновика и ответов |
| GET | `/api/business/tasks` | Task[] текущего бизнеса |
| GET | `/api/teams` | Team[] с вычисленным xp |
| POST | `/api/tasks/:id/proposals` | Proposal |
| GET | `/api/business/proposals?taskId=…` | Proposal[] текущего бизнеса |
| PATCH | `/api/proposals/:id` | Proposal; тело `{status:"accepted"}` или rejected |
| PATCH | `/api/proposals/:id/result` | Proposal; `{resultDescription,resultUrl}` |
| POST | `/api/proposals/:id/confirm-stage` | Proposal; `{acknowledged:true}` |

Подробные поля форм — в `HANDOFF-PARTICIPANT-3.md`. Все успешные запросы возвращают JSON с HTTP 200. Ошибки: `{error,code}`. Запись требует `Content-Type: application/json`, максимальный размер тела 64 KiB. Межсайтовые запросы записи запрещены.

Supabase хранит три таблицы. tasks содержит owner_id, полный Task в payload и revision; proposals — task_id, team_id, полный Proposal и revision; teams — профили. revision используется для условного обновления: конкурентная запись возвращает 409 вместо потери изменений. После подтверждения этапа его результат и статус нельзя менять; XP вычисляется из подтверждённых этапов, а не накапливается повторными инкрементами.

Браузерные роли не имеют доступа к таблицам. Включён RLS, доступ через SDK выполняется серверным ключом. SQL не удаляет существующие данные и добавляет пять синтетических команд. 5 черновиков, 5 опубликованных карточек и 5 откликов для окончательной демонстрации ещё предстоит подготовить с участником 3.

## AI

Для сохранения черновика также требуется `expectedRevision` из последнего ответа Task. Сервер сверяет клиентскую версию с сохранённой и возвращает 409 при устаревших данных. Gateway и очередь редактора обновляют revision после успешных операций. Это защищает и от пересекающихся запросов, и от сохранения старого снимка из второй вкладки.

Используется Responses API, Structured Outputs, `store:false`. Таймаут одной попытки 7 секунд, максимум две попытки, затем явно обозначенный `source:fallback`. При AI_MODE=mock, отсутствии ключа или модели возвращается резервный результат. Он не маскирует ошибки базы.

Для заполненных AI-полей проверяются цитаты-основания из пользовательского ввода. Это дополнительная проверка происхождения, а не гарантия смысловой точности: человек по-прежнему подтверждает карточку. Официальный рейтинг считает обычный серверный код.

```powershell
npm.cmd test

```

На запущенном приложении с настроенной базой:

```powershell
node scripts/smoke-backend.mjs
```

Скрипт создаёт временную задачу и отклик, проверяет сохранение, изоляцию подтверждённой версии и повторное подтверждение XP. В finally удаляет только свои записи по случайному UUID. Он не вызывает AI и не удаляет другие данные.
