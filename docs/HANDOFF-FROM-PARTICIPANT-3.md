# Передача части участника №3

## Готовые экраны и файлы

- `/catalog` (`src/app/catalog/page.tsx`): опубликованные подтверждённые карточки, официальный рейтинг, фильтры по отрасли и уровню, сортировка сервером или общей `listPublishedTasks`, обновление при возвращении на вкладку. Опубликованные 0–39 баллов остаются доступными.
- `/tasks/[id]` (`src/app/tasks/[id]/page.tsx`): все 14 полей, расшифровка оценки, профиль команды и форма отклика. Неопубликованная карточка не показывает форму. Локальный режим показывает собственные отклики выбранной команды и позволяет передать результат принятого этапа.
- `/business` (`src/app/business/page.tsx`): задачи текущего бизнеса, количество откликов, профили команд, независимые решения, предъявленный результат и явное подтверждение. После операции загружаются команды и XP из адаптера.
- Общие представления и стили: `src/components/catalog/`. Единый типизированный адаптер: `src/lib/collaboration-client.ts`. Синтетические примеры: `src/lib/collaboration-fixtures.ts`. В конструкторе добавлены два перехода через уже существующую функцию сохранения `navigate`, без изменения логики редактора.

## Запуск и режимы

`npm ci`, затем для локальной репетиции установите `NEXT_PUBLIC_DATA_MODE=local` и `NEXT_PUBLIC_COLLAB_FIXTURES=1` в `.env.local`, выполните `npm run dev`. Надпись «Демонстрационные данные» показывает явный режим фикстур. Публикации конструктора и каталог читают общий `sana-brief.tasks.v1` в `localStorage` одного браузера. Отклики сохраняются в отдельном `sana-brief.proposals.v1`. Без флага фикстур местные задачи и отклики начинаются пустыми. Данные между компьютерами не синхронизируются.

В режиме `NEXT_PUBLIC_DATA_MODE=api` используется только HTTP на том же origin с `credentials: include`, без локального успешного сохранения при ошибке. На текущей базе обработчики реализованы в `src/app/api/[...path]/route.ts`; подключение к работающему Supabase стенду в этой среде не проверено, поскольку `.env.local` с серверными ключами отсутствует. Следуйте `docs/BACKEND.md` для общей БД и пароля демостенда.

## Синтетические данные и сброс

`demoTasks()` возвращает **пять отдельных опубликованных задач и пять отдельных черновиков** со стабильными UUID. Опубликованные карточки: пекарня 100, учебный центр 80, мастерская 70, магазин 45, логистика 0 баллов. Эти баллы вычисляются общей `calculateScore`, а не прописаны в фикстуре. Пять разных профилей команд совпадают с `supabase/schema.sql`. Пять откликов включают два на пекарню; один принят и содержит предъявленный, но ещё не подтверждённый результат. Реальный XP у всех до подтверждения равен нулю.

При первом открытии локальных экранов фикстуры создаются только для отсутствующих ID через `gateway.create`; изменённые примеры и пользовательские задачи не перезаписываются. Кнопка «Сбросить демопримеры» в `/business` удаляет только известные ID задач и предложений, сохраняя пользовательские записи, и восстанавливает исходный демонстрационный набор. Перед импортом на общий сервер участник №2 может использовать содержимое `collaboration-fixtures.ts` и существующие API создания, подтверждения и публикации; сервер при этом сам рассчитывает официальный рейтинг. Не загружайте демоданные в рабочую базу без выбора тестового окружения.

## Контракты и точный запрос серверной части

`PublishedTask` используется из `src/lib/catalog.ts`; `Team`, `Proposal` и Zod-схемы — из `src/lib/collaboration-contracts.ts`. Новых копий общих типов и формулы оценки нет. HTTP-адаптер использует реализованные `GET /api/tasks`, `GET /api/catalog/:id`, `GET /api/teams`, `POST /api/tasks/:id/proposals`, `GET /api/business/tasks`, `GET /api/business/proposals`, `PATCH /api/proposals/:id`, `POST /api/proposals/:id/confirm-stage`.

**Недостающий контракт:** серверу нужен разрешённый способ прочитать командой собственные отклики по выбранной команде и отправить результат принятого отклика: например `GET /api/team/proposals?teamId=...` и `PATCH /api/team/proposals/:id/result`. Оба действия должны проверять серверную идентичность команды и связь с откликом. Текущий `GET /api/business/proposals` и `PATCH /api/proposals/:id/result` проверяют бизнес-владельца; клиент студента не вызывает их. Общий пароль демостенда и переключение UI не создают права отдельной команды. После согласования этих двух операций достаточно заменить методы `ownProposals` и `submitResult` HTTP-адаптера.

Текущий сервер блокирует изменение статуса и результата после подтверждения этапа, вычисляет +10 XP из подтверждённых откликов и делает повторное подтверждение идемпотентным. Экран соблюдает эти правила, но серверная конкуренция и Supabase в этой копии не проверялись.

## Пять минут показа

| Время | Действие |
|---|---|
| 0:00–0:35 | В `/tasks/new` показать слабое описание задачи пекарни. |
| 0:35–1:25 | Ответить на уточняющие вопросы подготовленными синтетическими сведениями. |
| 1:25–2:15 | В редакторе подтвердить наборы полей: контекст + потребность + результат = 35; затем пользователи, критерий, срок, ограничения и связь = 80; затем описание данных и доступ = 100. Значения показывает общая функция. |
| 2:15–2:55 | Опубликовать, перейти в `/catalog`, показать сортировку, фильтры и слабую опубликованную задачу с 0 баллами. |
| 2:55–3:40 | Открыть карточку, выбрать команду, отправить отклик и показать её профиль. |
| 3:40–4:25 | В `/business` сравнить два предложения на пекарню; вручную принять одну или обе команды. |
| 4:25–4:45 | В локальном режиме команда передаёт результат со своей карточки; бизнес ставит галочку и подтверждает этап. Показать XP из источника данных. В подготовленной фикстуре результат первого отклика уже предъявлен. |
| 4:45–5:00 | Показать код, ограничения общего демодоступа и правила подтверждения. |

Время участника №3 — от публикации в каталоге до XP, 2:15–4:45. В API-режиме передачу результата со стороны команды показывать после добавления указанных серверных маршрутов; не выдавать бизнесовый обработчик за командный.
