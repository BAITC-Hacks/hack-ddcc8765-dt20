## Твоя область работы

1. `/catalog`: общий каталог опубликованных задач, рейтинг, фильтры, состояния загрузки/ошибки/пустого результата.
2. `/tasks/[id]`: полная подтверждённая карточка и форма отклика от выбранной демокоманды.
3. `/business`: задачи бизнеса, список откликов, профили команд, принять/отклонить, результат этапа и его подтверждение.
4. Отображение XP команды, полученных только за подтверждённые этапы.
5. Синтетические примеры и пяти­минутная демонстрация сквозного сценария.

Участник 1 делает конструктор и редактор; участник 2 — сервер, базу, AI и окончательную проверку правил. Общие типы и зависимости меняются через участника 2.

## Данные каталога: PublishedTask

```ts
type PublishedTask = {
  id: string;
  confirmedContent: TaskContent;
  confirmedIndustry: string;
  confirmedScore: Score;
  confirmedAt: string; // ISO 8601
  publishedAt: string; // ISO 8601
};
```

Поля карточки `TaskContent` — строки. Неизвестное значение в сохранённой карточке — пустая строка; в интерфейсе показывать «Не указано». AI может возвращать null, но преобразование выполняется до передачи карточки этим экранам.

| Поле | Что показывать |
|---|---|
| `title` | Название |
| `context` | Текущая ситуация |
| `need` | Что нужно изменить |
| `users` | Для кого делается решение |
| `dataDescription` | Доступные материалы |
| `dataAccess` | Источник или способ доступа |
| `expectedResult` | Что должна передать команда |
| `successMetric` | Показатель проверки |
| `successTarget` | Целевое значение или условие приёмки |
| `deadline` | Срок |
| `constraints` | Ограничения |
| `contact` | Контакт бизнеса |
| `interaction` | Формат консультаций |
| `feedback` | Порядок обратной связи |

В полном объекте Task у редактора есть draft, rawText, answers и другие поля. Каталог получает только PublishedTask: неподтверждённые правки и ответы не следует включать в публичный ответ.

## Рейтинг и фильтры

Тип Score уже определён в `src/lib/contracts.ts`:

```ts
type Score = {
  total: number;
  level: "draft" | "working" | "ready" | "priority";
  groups: {
    id: string;
    label: string;
    earned: number;
    max: number;
    missing: { field: keyof TaskContent; label: string; points: number }[];
  }[];
};
```

| Значение level | Баллы | Подпись |
|---|---|---|
| `draft` | 0–39 | Требует уточнения |
| `working` | 40–69 | Рабочая задача |
| `ready` | 70–89 | Готова к работе |
| `priority` | 90–100 | Приоритетная задача |

`draft` здесь — уровень готовности. Видимость определяет факт публикации, поэтому опубликованную карточку с 0 баллов показываем и принимаем отклики на неё.

Сортировка: баллы по убыванию, затем время публикации от новых к старым, затем id по возрастанию. Фильтры: подтверждённая отрасль и level. При сбросе фильтров должны вернуться все опубликованные задачи. Список отраслей брать из существующего INDUSTRIES.

Предварительный рейтинг редактора не использовать как официальный. После подтверждения правок обновлять каталог и детальную карточку, чтобы показать новый рейтинг и порядок.

## Общие типы команд и откликов

Типы и Zod-схемы находятся в `src/lib/collaboration-contracts.ts`: импортировать Team, Proposal, teamSchema и proposalSchema оттуда. Не создавать расходящиеся копии в каждом компоненте.

```ts
type Team = {
  id: string;
  name: string;
  interests: string[];
  skills: string[];
  technologies: string[];
  xp: number; // вычисляется сервером по подтверждённым этапам
};

type Proposal = {
  id: string;
  taskId: string;
  teamId: string;
  idea: string;
  plan: string;
  deadline: string;
  prototypeUrl: string | null;
  status: "pending" | "accepted" | "rejected";
  resultDescription: string | null;
  resultUrl: string | null;
  stageConfirmedAt: string | null;
  createdAt: string;
};
```

Форма отклика: выбор демокоманды, идея, план выполнения, срок, необязательная ссылка на прототип. Начальный status задаёт сервер: pending. Клиент не передаёт начисленные XP или дату подтверждения.

## Реализованные API для участника 3

Все успешные операции возвращают JSON; после записи не ожидаем 204. Запросы идут на тот же origin с `credentials: "include"`. Секреты OpenAI и Supabase клиенту не нужны.

Импортируйте `collaborationGateway` и `CollaborationApiError` из `src/lib/collaboration-gateway.ts`. Методы `catalog(filters)`, `publicTask(id)`, `teams()`, `proposals(taskId?)`, `propose(taskId, input)`, `decide(id, status)`, `result(id, input)`, `confirmStage(id)` соответствуют таблице ниже. Ответы проходят проверку Zod. Ошибка содержит `code`, HTTP `status` (либо `null` для сети, таймаута и неверного ввода) и `message`. `INVALID_RESPONSE` означает несовместимый ответ сервера. Клиент не подменяет сбой локальными данными. При настройке `NEXT_PUBLIC_API_BASE_URL` допустим относительный путь; без него запросы используют `/api/...` на том же origin. Таймаут — 20 секунд.

| Метод и URL | Вход | Ответ | Состояние |
|---|---|---|---|
| `GET /api/tasks` | `industry`, `level` в query по желанию | `PublishedTask[]` | Реализовано |
| `GET /api/catalog/:id` | id задачи | `PublishedTask` | Реализовано |
| `GET /api/teams` | Нет | `Team[]` | Реализовано |
| `POST /api/tasks/:id/proposals` | `{ teamId, idea, plan, deadline, prototypeUrl }` | `Proposal` | Реализовано |
| `GET /api/business/tasks` | Нет | `Task[]` текущего бизнеса | Реализовано |
| `GET /api/business/proposals` | `taskId` в query по желанию | `Proposal[]` для задач текущего бизнеса | Реализовано |
| `PATCH /api/proposals/:id` | `{ status: "accepted" \| "rejected" }` | `Proposal` | Реализовано |
| `PATCH /api/proposals/:id/result` | `{ resultDescription, resultUrl }` | `Proposal` | Реализовано |
| `POST /api/proposals/:id/confirm-stage` | `{ acknowledged: true }` | `Proposal` с датой подтверждения | Реализовано |

`GET /api/tasks/:id` уже согласован с участником 1 для редактора и возвращает полный Task. Для студенческого экрана предлагаем отдельный `/api/catalog/:id`, чтобы не отдавать неподтверждённые данные.

Пример отправки отклика:

```json
{
  "teamId": "00000000-0000-4000-8000-000000000001",
  "idea": "Сделать веб-форму приёма заказов",
  "plan": "Изучить CSV, собрать форму, проверить на 20 примерах",
  "deadline": "7 дней",
  "prototypeUrl": null
}
```

Предлагаемый единый формат ошибки:

```json
{
  "error": "Не удалось сохранить отклик. Попробуйте ещё раз.",
  "code": "STORAGE_UNAVAILABLE"
}
```

Статусы: 400 — некорректные данные; 403 — запрещён межсайтовый запрос; 404 — объект недоступен или отсутствует; 409 — операция конфликтует с состоянием; 413 — тело больше 64 KiB; 415 — требуется application/json; 429 — слишком частые AI-запросы; 503 — сервис недоступен. В деморежиме один бизнес-профиль задаётся сервером. Стенд открыт без логина и пароля; все посетители могут разыгрывать обе роли. Подробности в BACKEND.md.

## Выбор команд и XP

- Можно принять одну, несколько или ни одной команды. Принятие одного отклика не отключает кнопки остальных.
- Отклонение всех предложений допустимо; автоназначения команды нет.
- Кнопка подтверждения результата доступна только для принятой команды и после предъявления результата.
- После подтверждения этапа обновить отклик и повторно загрузить Team с сервера.
- Для MVP предложено +10 XP за один этап. Повторное нажатие или повтор сетевого запроса не меняют итог второй раз.
- На время запроса блокировать повторное нажатие и показывать загрузку. Если запрос завершился ошибкой, состояние не должно выглядеть успешно сохранённым.
- Не увеличивать XP простым `xp + 10` в браузере. Показывать серверное значение.

Клиент принимает в теле `propose` только `teamId`, `idea`, `plan`, `deadline`, `prototypeUrl`; в `result` только `resultDescription`, `resultUrl`. `status` для нового отклика, `xp` и системные даты задаёт сервер. Лишние поля клиент отклоняет до отправки.

## Состояния интерфейса

Для каждого экрана нужны загрузка, ошибка с повтором и пустое состояние. Текст формы не очищать при сетевой ошибке. При фильтре без результатов показать сброс фильтров. Отсутствующую/неопубликованную задачу не изображать как пустую доступную карточку.

В локальном режиме данные localStorage не синхронизируются между компьютерами. Для интеграции нужен настоящий API и общая база. Ошибка серверного сохранения не должна автоматически заменяться успешным локальным сохранением.

## Демоданные и показ

Подготовлен скрипт `npm run seed:demo` для идемпотентной загрузки синтетических данных в согласованную схему. Он использует детерминированные имена и идентификаторы, `ignoreDuplicates` и не перезаписывает существующие записи. Демо-набор включает:

- 5 отдельных черновиков и 5 опубликованных карточек;
- примеры всех четырёх уровней, включая опубликованную задачу 0–39;
- 5 команд с разными интересами и технологиями;
- 5 откликов, минимум два — на одну задачу;
- один результат этапа, который можно предъявить и подтвердить;
- только синтетические контакты и данные. Баллы вычисляются общей функцией.

Сценарий: пекарня → описание → вопросы → карточка → подтверждение → 35/80/100 → публикация → каталог → отклик → сравнение команд → ручной выбор → подтверждение результата → XP.

Проверка API: `npm run smoke:backend`. Проверка происхождения AI: `npm run check:ai -- --expect=ai` или `--expect=fallback`. Эти команды требуют Node.js 22.15+ и настроенного сервера с переменными из `docs/BACKEND.md`. Настройка live/mock не изменилась, новых пакетов и миграций базы для проверки качества нет.
