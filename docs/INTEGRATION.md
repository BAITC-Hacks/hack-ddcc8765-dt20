# Интеграция бизнес-редактора, сервера и каталога

Статус на 23 сентября 2026: бизнес-редактор, каталог, публичная карточка, кабинеты бизнеса и команды объединены с обработчиками задач, AI и совместной работы. Проверены реальные AI-запросы, запись демоданных в Supabase и сквозной HTTP-сценарий на настроенном окружении разработчика. Это не проверка отдельного публичного стенда. Экраны используют `src/lib/collaboration-gateway.ts` и общую бизнес-логику `src/lib/task-service.ts`.

## Дополнение участника 2: версии запросов

Серверные операции реализованы; настройка описана в `BACKEND.md`. Полный Task теперь содержит `revision` — серверную версию. При PATCH черновика отправлять `{...DraftInput, expectedRevision: task.revision}`; при подтверждении — `{acknowledged:true, expectedRevision: task.revision}`; при публикации — `{expectedRevision: task.revision}`. Создание остаётся `{id,...DraftInput}`. Использовать revision из последнего успешного ответа. Устаревшая версия возвращает 409, а неподтверждённые правки остаются в форме. Gateway и очередь сохранений редактора обновлены. Это дополнение заменяет тела confirm/publish/draft в исходной таблице ниже.

Интерфейс бизнеса подключён к серверу через `src/lib/gateway.ts`; общие типы и схемы находятся в `src/lib/contracts.ts`.

## Режимы

```dotenv
NEXT_PUBLIC_DATA_MODE=api
NEXT_PUBLIC_API_BASE_URL=
```

Пустой URL означает тот же origin и `/api/...`. Если API находится отдельно, укажите базовый HTTPS-адрес без завершающего `/`; настройте CORS для origin интерфейса и cookie, если они используются. Режим фиксируется при сборке; после изменения `.env.local` перезапустите сервер.

По просьбе владельца `.env.local` временно отслеживается в приватном хакатонном репозитории для общей среды команды. Серверные ключи не должны использовать префикс `NEXT_PUBLIC_` и не должны попадать в публичный репозиторий или браузерный код.

`local` — самостоятельная демонстрация без AI и общей базы. `api` — HTTP-сохранение и AI-обработчики участника №2. Ошибка API не превращается в успешное локальное сохранение. Таймаут запросов редактора — 45 секунд, клиента каталога — 20 секунд. Ответы проверяются Zod.

## Тип карточки

Все значения `TaskContent` в сохранённой задаче — строки; неизвестное значение — пустая строка. AI-ответу разрешён `null`, который адаптер преобразует в пустую строку.

```ts
type TaskContent = {
  title: string;
  context: string;
  need: string;
  users: string;
  dataDescription: string;
  dataAccess: string;
  expectedResult: string;
  successMetric: string;
  successTarget: string;
  deadline: string;
  constraints: string;
  contact: string;
  interaction: string;
  feedback: string;
};
```

Полный `Task` содержит `id`, `revision`, `rawText`, `industry`, `draft`, `questions`, `answers`, `step`, `source`, `updatedAt`, `confirmedContent`, `confirmedIndustry`, `confirmedAt`, `confirmedScore`, `publishedAt`, а также необязательное `qualityReview`. Подтверждённые поля до подтверждения/публикации равны `null`. Даты возвращаются ISO-строками.

## Операции API

Все операции возвращают JSON, в том числе после сохранения. Не возвращайте `204`: адаптер ожидает проверяемый объект.

| Метод и путь                  | Тело                                               | Ответ                            |
| ----------------------------- | -------------------------------------------------- | -------------------------------- |
| `POST /api/tasks`             | `{id, ...DraftInput}`                              | Полный `Task`                    |
| `GET /api/tasks/:id`          | —                                                  | Полный `Task`                    |
| `GET /api/business/tasks`     | —                                                  | `Task[]` текущего бизнес-профиля |
| `PATCH /api/tasks/:id/draft`  | `{...DraftInput, expectedRevision}`                | Полный `Task`                    |
| `POST /api/ai/questions`      | `{rawText, industry, content}`                     | `{questions, source}`            |
| `POST /api/ai/card`           | `{rawText, industry, content, questions, answers}` | `{content, source}`              |
| `POST /api/ai/quality`        | `{content, industry}`                              | `QualityReview`                  |
| `POST /api/tasks/:id/review`  | `{expectedRevision}`                               | Полный `Task`                    |
| `POST /api/tasks/:id/confirm` | `{acknowledged: true, expectedRevision}`           | Полный `Task`                    |
| `POST /api/tasks/:id/publish` | `{expectedRevision}`                               | Полный `Task`                    |

`DraftInput` — только `rawText`, `industry`, `draft`, `questions`, `answers`, `step`, `source`. Клиент не передаёт официальный рейтинг, отметку публикации или подтверждённые поля через сохранение черновика. Сохранения сериализованы внутри вкладки; перед подтверждением интерфейс дожидается записи текущего черновика.

### Защита от перезаписи между вкладками

`PATCH /draft`, `POST /confirm` и `POST /publish` передают `expectedRevision` в JSON-теле из последнего успешного ответа `Task.revision`. Сервер атомарно сравнивает версию, увеличивает её при записи и возвращает новое значение. Очередь `DraftSaver` использует свежую версию для следующей записи, даже если сохранение было поставлено в очередь до получения предыдущего ответа. Заголовок `If-Match` не требуется.

При несовпадении сервер возвращает `409`, не меняя запись. Интерфейс останавливает автосохранение и предлагает сохранить введённые правки отдельным черновиком либо явно отбросить их и открыть сохранённую версию.

В локальном режиме проверка версии и запись защищены Web Locks для всего хранилища задач. Нужны HTTPS или localhost и браузер с поддержкой Web Locks. При отсутствии блокировок приложение сообщает об ошибке, а не выполняет небезопасную запись.

`POST /api/tasks` получает UUID от клиента и повторяемо создаёт задачу по этому id для текущего владельца. Сервер устанавливает владельца по общей демосессии, а не по присланному клиентом `owner_id`, и проверяет доступ к задачам при чтении и изменении. Индивидуальной авторизации по ролям в демостенде нет.

## Уточняющие вопросы

```json
{
  "questions": [
    {
      "id": "users",
      "field": "users",
      "text": "Кто будет пользоваться решением?",
      "hint": "Роль и задача пользователя"
    },
    {
      "id": "data",
      "field": "dataDescription",
      "text": "Какие материалы доступны команде?"
    },
    {
      "id": "result",
      "field": "expectedResult",
      "text": "Какой результат вы хотите получить?"
    }
  ],
  "source": "ai"
}
```

Требования: 3–8 вопросов, уникальные `id`, `field` из ключей карточки, непустой текст. `answers` — объект `{[questionId]: string}`. `source` принимает `ai` или `fallback`; UI использует его, чтобы честно обозначать происхождение результата.

При повторном получении вопросов интерфейс сохраняет ответ только при полном совпадении ID, поля, текста вопроса и подсказки. Для изменённого или нового вопроса ответ очищается: повторно использованный моделью ID не должен переносить старый ответ в другое поле. Это правило применяется и при переходе к шаблонным вопросам.

AI-сборка карточки переносит только сведения, подтверждённые точными непрерывными фрагментами исходного текста: значение поля должно входить в свою цитату, а цитата — в исходные данные; различия в пробелах допускаются. Неизвестное остаётся `null` в ответе AI и пустой строкой в сохранённом `TaskContent`. При ошибке AI интерфейс предлагает явно продолжить с шаблонными вопросами или локальной сборкой карточки. При этом API-режим сохранения не выключается. Ошибку серверного хранения резервный AI не маскирует.

## Проверка качества полей

`qualityReview` имеет схему `src/lib/quality-contracts.ts`: `{source: "ai" | "fallback", version: "quality-v1", inputKey, checkedAt, fields: [{field, accepted, reason, suggestion}]}`. `inputKey` — точный канонический идентификатор содержимого и отрасли. Не показывайте его пользователю и не записывайте в логи. После изменения содержимого или отрасли прежняя проверка недействительна. Сервер повторно использует проверку только для точно совпадающего содержимого. `source: "fallback"` честно обозначает детерминированную проверку при недоступности AI.

Решения обязательны для всех 13 полей: `context`, `need`, `users`, `dataDescription`, `dataAccess`, `expectedResult`, `successMetric`, `successTarget`, `deadline`, `constraints`, `contact`, `interaction`, `feedback`. Модель получает отдельный русскоязычный промпт с неизменными критериями; текст задачи рассматривается как данные, включая просьбы повысить рейтинг. Результат проверяется по схеме, а расчёт баллов остаётся в коде.

Проверка запускается явной кнопкой или при ручном подтверждении карточки. Подтверждение остаётся действием человека. Предварительный рейтинг учитывает принятые проверкой поля; официальный рейтинг сервер вычисляет по фиксированным весам только после подтверждения. ИИ не назначает баллы и может лишь отклонить поле, которое прошло базовую проверку. Слабый рейтинг не запрещает публикацию. Интерфейс даёт запросу 45 секунд; сервер делает до двух попыток к AI по 18 секунд.

## Подтверждение и публикация

При подтверждении сервер:

1. Проверяет доступ пользователя, явное согласие и название задачи.
2. Валидирует текущий черновик по ограничениям контракта.
3. Копирует `draft` в `confirmedContent`, отрасль — в `confirmedIndustry`.
4. Получает или повторно использует проверку качества точного текущего содержимого, пересчитывает `confirmedScore` по принятым полям и сохраняет `confirmedAt`.
5. Возвращает полный обновлённый объект. Если задача уже опубликована, каталог должен увидеть новую подтверждённую версию.

При публикации проверяет наличие подтверждения и отсутствие изменений относительно `confirmedContent`/`confirmedIndustry`, затем задаёт `publishedAt`. **Порога рейтинга нет.** Повторная публикация не должна создавать вторую задачу.

Подтверждённый `Score` содержит `total`, `level` и семь групп `groups`. Каждая группа: `id`, `label`, `earned`, `max`, `missing: [{field, label, points}]`. Идентификаторы и веса: `context:20`, `data:20`, `result:15`, `success:15`, `constraints:10`, `users:10`, `contact:10`. UI проверяет согласованность суммы, весов и уровня. Эталонный расчёт находится в `scoring.ts`; его можно использовать на сервере. Формат контакта и текстовые проверки нужны для воспроизводимости, но не являются смысловой экспертизой.

## Каталог и совместная работа

- Редактор доступен по `/tasks/[id]/edit`.
- Для каталога сервер выбирает задачи с ненулевым `publishedAt` и отображает **`confirmedContent`**, **`confirmedIndustry`**, **`confirmedScore`**.
- Не используйте `draft` для публичных карточек: там могут находиться ещё не подтверждённые правки.
- Сортируйте по `confirmedScore.total` по убыванию. При равенстве используйте стабильный порядок по времени публикации и id.
- Уровень `draft` означает 0–39 баллов готовности; он не скрывает опубликованную карточку.
- После публикации и подтверждённого дополнения обновляйте данные каталога.
- Маршруты `/catalog`, `/tasks/[id]`, `/business` и `/student` реализуют каталог, отклики, выбор команд, предъявление результатов и подтверждение этапов с XP.
- В локальном режиме `gateway.list()` возвращает сохранённые задачи; демопримеры добавляются отдельным действием в каталоге. Событие `sana:tasks-changed` сообщает об изменениях в той же вкладке. Между браузерами localStorage не синхронизируется.

## Границы этой части

Общий демонстрационный доступ позволяет переключаться между ролями, но не даёт индивидуальных аккаунтов и разграничения прав команд. Для полноценного публичного сервиса потребуются пользовательские сессии и права по ролям. Серверные секреты остаются на сервере без префикса `NEXT_PUBLIC_`.
