# Интеграция части участника №1

## Дополнение участника 2: версии запросов

Серверные операции реализованы; настройка описана в `BACKEND.md`. Полный Task теперь содержит `revision` — серверную версию. При PATCH черновика отправлять `{...DraftInput, expectedRevision: task.revision}`; при подтверждении — `{acknowledged:true, expectedRevision: task.revision}`; при публикации — `{expectedRevision: task.revision}`. Создание остаётся `{id,...DraftInput}`. Использовать revision из последнего успешного ответа. Устаревшая версия возвращает 409, а неподтверждённые правки остаются в форме. Gateway и очередь сохранений редактора обновлены. Это дополнение заменяет тела confirm/publish/draft в исходной таблице ниже.

Интерфейс бизнеса готов к подключению сервера. Все сетевые вызовы собраны в `src/lib/gateway.ts`, общие типы и схемы — в `src/lib/contracts.ts`.

## Режимы

```dotenv
NEXT_PUBLIC_DATA_MODE=api
NEXT_PUBLIC_API_BASE_URL=
```

Пустой URL означает тот же origin и `/api/...`. Если API находится отдельно, укажите базовый HTTPS-адрес без завершающего `/`; настройте CORS для origin интерфейса и cookie, если они используются. Режим фиксируется при сборке; после изменения `.env.local` перезапустите сервер.

`local` — самостоятельная демонстрация без AI и общей базы. `api` — HTTP-сохранение и AI-обработчики участника №2. Ошибка API не превращается в успешное локальное сохранение. Таймаут запроса — 20 секунд. Ответы проверяются Zod.

## Тип карточки

Все значения `TaskContent` в сохранённой задаче — строки; неизвестное значение — пустая строка. AI-ответу разрешён `null`, который адаптер преобразует в пустую строку.

```ts
type TaskContent = {
  title: string;
  context: string;
  need: string;
  users: string;
  dataDescription: string;
  dataAccess: string;
  expectedResult: string;
  successMetric: string;
  successTarget: string;
  deadline: string;
  constraints: string;
  contact: string;
  interaction: string;
  feedback: string;
};
```

Полный `Task` содержит `id`, `rawText`, `industry`, `draft`, `questions`, `answers`, `step`, `source`, `updatedAt`, `confirmedContent`, `confirmedIndustry`, `confirmedAt`, `confirmedScore`, `publishedAt`. Последние пять полей до подтверждения/публикации равны `null` согласно типам. Даты возвращаются ISO-строками.

## Операции API

Все операции возвращают JSON, в том числе после сохранения. Не возвращайте `204`: адаптер ожидает проверяемый объект.

| Метод и путь                  | Тело                                               | Ответ                            |
| ----------------------------- | -------------------------------------------------- | -------------------------------- |
| `POST /api/tasks`             | `{id, ...DraftInput}`                              | Полный `Task`                    |
| `GET /api/tasks/:id`          | —                                                  | Полный `Task`                    |
| `GET /api/business/tasks`     | —                                                  | `Task[]` текущего бизнес-профиля |
| `PATCH /api/tasks/:id/draft`  | `DraftInput`                                       | Полный `Task`                    |
| `POST /api/ai/questions`      | `{rawText, industry, content}`                     | `{questions, source}`            |
| `POST /api/ai/card`           | `{rawText, industry, content, questions, answers}` | `{content, source}`              |
| `POST /api/tasks/:id/confirm` | `{acknowledged: true}`                             | Полный `Task`                    |
| `POST /api/tasks/:id/publish` | `{}`                                               | Полный `Task`                    |

`DraftInput` — только `rawText`, `industry`, `draft`, `questions`, `answers`, `step`, `source`. Клиент не передаёт официальный рейтинг, отметку публикации или подтверждённые поля через сохранение черновика. Сохранения сериализованы внутри вкладки; перед подтверждением интерфейс дожидается записи текущего черновика.

`POST /api/tasks` получает UUID от клиента. Сделайте создание повторяемым по этому id для текущего владельца. Сервер устанавливает владельца по своей демосессии/авторизации, а не по присланному клиентом `owner_id`. Проверяйте доступ к задачам и их изменение на сервере.

## Уточняющие вопросы

```json
{
  "questions": [
    {
      "id": "users",
      "field": "users",
      "text": "Кто будет пользоваться решением?",
      "hint": "Роль и задача пользователя"
    },
    {
      "id": "data",
      "field": "dataDescription",
      "text": "Какие материалы доступны команде?"
    },
    {
      "id": "result",
      "field": "expectedResult",
      "text": "Какой результат вы хотите получить?"
    }
  ],
  "source": "ai"
}
```

Требования: 3–8 вопросов, уникальные `id`, `field` из ключей карточки, непустой текст. `answers` — объект `{[questionId]: string}`. `source` принимает `ai` или `fallback`; UI использует его, чтобы честно обозначать происхождение результата.

При ошибке AI интерфейс предлагает явно продолжить с шаблонными вопросами или локальной сборкой карточки. При этом API-режим сохранения не выключается. Сломанный сервер хранения нужно исправить, а не маскировать резервным AI.

## Подтверждение и публикация

При подтверждении сервер:

1. Проверяет доступ пользователя, явное согласие и название задачи.
2. Валидирует текущий черновик по ограничениям контракта.
3. Копирует `draft` в `confirmedContent`, отрасль — в `confirmedIndustry`.
4. Пересчитывает `confirmedScore` обычным кодом и сохраняет `confirmedAt`.
5. Возвращает полный обновлённый объект. Если задача уже опубликована, каталог должен увидеть новую подтверждённую версию.

При публикации проверяет наличие подтверждения и отсутствие изменений относительно `confirmedContent`/`confirmedIndustry`, затем задаёт `publishedAt`. **Порога рейтинга нет.** Повторная публикация не должна создавать вторую задачу.

Подтверждённый `Score` содержит `total`, `level` и семь групп `groups`. Каждая группа: `id`, `label`, `earned`, `max`, `missing: [{field, label, points}]`. Идентификаторы и веса: `context:20`, `data:20`, `result:15`, `success:15`, `constraints:10`, `users:10`, `contact:10`. UI проверяет согласованность суммы, весов и уровня. Эталонный расчёт находится в `scoring.ts`; его можно использовать на сервере. Формат контакта и текстовые проверки нужны для воспроизводимости, но не являются смысловой экспертизой.

## Передача участнику №3

- Редактор доступен по `/tasks/[id]/edit`.
- Для каталога сервер выбирает задачи с ненулевым `publishedAt` и отображает **`confirmedContent`**, **`confirmedIndustry`**, **`confirmedScore`**.
- Не используйте `draft` для публичных карточек: там могут находиться ещё не подтверждённые правки.
- Сортируйте по `confirmedScore.total` по убыванию. При равенстве используйте стабильный порядок по времени публикации и id.
- Уровень `draft` означает 0–39 баллов готовности; он не скрывает опубликованную карточку.
- После публикации и подтверждённого дополнения обновляйте данные каталога.
- Маршруты `/catalog`, `/tasks/[id]` и `/business` остаются свободными для каталога, откликов и кабинета бизнеса.
- В локальном прототипе `gateway.list()` возвращает демозадачи; событие `sana:tasks-changed` сообщает об изменениях в той же вкладке. Между браузерами localStorage не синхронизируется.

## Границы этой части

В реализации участника №1 нет общего сервера, подключения Supabase, реальной модели, регистрации, каталога, откликов и выбора команды. Есть работающий UI, локальный демонстрационный сценарий и HTTP-контракт. Для серверных секретов нельзя использовать `NEXT_PUBLIC_*`.
